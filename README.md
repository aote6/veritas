# Veritas

**A Deterministic State Evolution Machine**

---

## The Question

Every programmable system ultimately answers to hardware. Hardware does not
negotiate. It executes what it is given, deterministically, every time.

Assembly was supposed to be the closest thing to that hardware truth. It
isn't. Assembly is a menu — the words on it could be swapped for anything,
and the machine underneath would not care. Naming an instruction does not
constrain what actually happens when it runs.

Veritas started from one question: if hardware is the only layer that
truly cannot be argued with, what would it mean to build a software system
that inherits that same property — not fast, not feature-rich, but
**incapable of lying about what happened**?

## What Veritas Is

Veritas is a kernel where every state change is:

- **Deterministic** — the same input, the same program, always the same result
- **Verifiable** — the result can be checked, not just trusted
- **Reproducible** — a different machine, given the same inputs, arrives at
  the same state
- **Attributable** — every change traces back to the transaction and
  instruction that caused it

This is not a virtual machine competing with JVM or WASM. It is not a
blockchain. It is not a database. Those are all implementation shapes
Veritas passed through and discarded on the way to its actual purpose:
software that can prove its own evolution, instruction by instruction,
transaction by transaction.

## The Model

```
Instruction
    |
    v
Verified Execution
    |
    v
Transaction
    |
    v
Deterministic State Transition
    |
    v
State Root (proof)
```

Traditional software execution answers "what happened." Veritas is built to
also answer "why is this the only thing that could have happened, given
this program and this input" — and to let another machine check that claim
independently, without trusting the first machine's word for it.

## Why This, Now

Software is entering a period where the code itself is cheap to produce —
generated, modified, and regenerated by systems other than the original
author, at a pace no human review process was built to match.

The bottleneck is no longer "can this system be changed."
It is "can this system prove that a change preserved what mattered."

Veritas exists to be the layer that answers that second question — a
foundation where a change (by a human or an AI) is not accepted because
someone said it was fine, but because the state transition it produced can
be independently re-derived and checked against an invariant.

## Design Commitments

These do not change as the implementation evolves. They are the constraints
Veritas holds itself to, regardless of what module, instruction set, or
storage engine sits underneath at any given time:

1. **Guarantees before performance.** A faster wrong answer is not an
   improvement.
2. **Explicit over implicit.** If a rule changes system behavior, it must
   be something a caller opts into, not a default silently inherited by
   everyone already depending on the old behavior.
3. **No privileged shortcuts.** Neither a human operator nor an AI agent
   modifying this system gets to bypass verification because they are
   presumed trustworthy. Trust is not the mechanism — proof is.
4. **A state root is a claim, not a formality.** If two independent
   executions produce the same root, that equivalence must mean something
   checkable, not just something printed.
