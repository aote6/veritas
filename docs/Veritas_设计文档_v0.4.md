项目代号：Veritas
文档版本：0.7（代码实现同步）
状态：定版，Rust原型开发中

零、设计原则

三条原则贯穿所有设计决策。

原则一：保证优先于性能。
第一阶段的唯一目标是语义正确性。慢但正确，优于快但有漏洞。

原则二：原语最小化。
每条原语必须通过"删除测试"：如果删除它，是否有某条机器保证无法实现？不能通过测试的原语不是原语。

原则三：不可绕过优先于便利性。
强制流程不提供任何后门或绕过机制。显式声明优于隐式推断——机器只保护程序员显式声明的东西。机器世界里没有"警告"，只有"允许"和"拒绝"。

一、机器承诺

Veritas 抽象机器向所有运行于其上的程序做出以下不可动摇的保证：

1. 契约强制执行
任何模块间的调用，其前置条件和后置条件均由机器自动检查。静态契约在组合时验证，动态契约在运行时验证。条件不满足，调用不会发生。

2. 能力边界不可突破
模块访问任何受保护资源，必须持有对应能力凭证。能力凭证的构造器不对宿主语言开放，仅由机器的GRANT原语生成。能力状态纳入事务模型，受快照隔离和WAL保护。

3. 事务原子性与并发安全
事务满足原子性：全部成功提交或全部自动回滚。并发事务之间，机器自动进行读-写反依赖冲突检测。对于显式声明的动态集合不变量，机器提供幻读级别的写偏斜保护。副作用暂存至提交成功后执行，携带系统级幂等键。提交临界区保证冲突检测、WAL写入、状态固化三步不可分割。

4. 状态变更可追溯且可恢复
每一次状态修改，机器自动记录到WAL。系统崩溃重启后，机器根据WAL自动恢复至最近的一致性状态。能力状态变更、副作用执行确认同样受此保证。

5. 组合即验证
模块组合时，机器在组合期自动检查静态契约兼容性。任何不兼容均在组合期被直接拒绝。

二、核心对象

对象 定义 关键属性
模块 代码与契约的封装单元，无状态的只读逻辑集合 模块不持有可变数据；所有状态属于机器的全局状态树
状态 模块内部的可变数据，存储于机器全局状态树 每个状态由StateId唯一标识；绑定所有者模块；跨模块访问需能力凭证；维护独立版本号
静态契约 组合期可验证的约束 包括：能力需求声明、接口签名、不可变约束声明、重入许可声明。重入声明不一致直接拒绝组合
动态契约 运行时受状态驱动的约束 包括：前置条件、后置条件、模块不变量。由宿主语言纯函数实现，禁止副作用
不变量作用域 显式声明的跨状态保护域，绑定动态集合 通过ScopeRegistry维护成员关系；集合结构版本号独立于成员状态版本号，用于幻读防御
读取集 事务自动追踪的状态读取记录 记录StateId及读取时的版本号；涉及ENUM_SCOPE时同时记录Scope的结构版本号
写入集 事务暂存的状态修改 仅存在于内存暂存区；COMMIT时合并写入WAL；ROLLBACK_TO可部分清空
能力 不透明凭证，CapabilityId(u64) 构造器不对宿主开放；由GRANT生成；内部维护委托图（确定性哈希生成，见运行时标准1.4节）
能力委托图 能力授权关系的有向森林 记录授权者→被授权者关系；每个(cap_id, holder)唯一；REVOKE默认级联；崩溃恢复时从WAL重建
事务 一组操作的原子执行边界 绑定快照版本号、读取集、写入集、副作用队列
副作用队列 事务内暂存的对外操作 COMMIT成功后才执行；每条携带系统幂等键{事务ID}-{序列号}
预写日志(WAL) 崩溃恢复的物理基础 记录最终提交的变更（含scope变更和effect内容）；包含EFFECT执行确认记录
全局提交临界区 COMMIT的原子执行区间 冲突检测→写WAL→状态固化，三步不可分割

三、不可绕过的强制流程

流程1：状态修改

任何状态修改操作：
  → 检查：当前是否处于事务上下文中？
    否 → 拒绝。状态修改必须在事务内进行
    是 → 继续
  → 检查：调用者是否持有该状态的能力凭证？
    检查依据：事务快照内的能力状态
    否 → 拒绝
    是 → 继续
  → 将修改写入当前事务的内存暂存写入集
  → 检查：修改后是否违反所属模块的局部不变量？
    是 → 事务标记为"可中止"
    否 → 继续
  → 检查：修改是否涉及已声明的INVARIANT_SCOPE的集合成员结构变更？
    是 → 将该SCOPE的结构变更标记纳入写入集
    否 → 继续

流程2：模块调用

模块A调用模块B的公开操作：
  → 检查：当前事务调用栈中是否已存在模块B？
    是 → 检查：模块B是否声明了REENTRANT_ALLOW？
      否 → ABORT：检测到未声明的重入
      是 → 继续
    否 → 继续
  → 检查：模块A是否持有调用模块B的能力凭证？
    否 → 拒绝调用
    是 → 继续
  → 执行模块B声明的所有REQUIRE条件
    机器隐式行为：将REQUIRE中涉及的状态读取自动记录到读取集
  → 检查：当前状态是否满足所有前置条件？
    否 → 拒绝调用
    是 → 继续
  → 执行模块B的操作体
  → 执行模块B声明的所有ENSURE条件
  → 检查：执行后状态是否满足所有后置条件？
    否 → 调用失败，事务标记为"可中止"
    是 → 继续
  → 返回结果给模块A

流程3：模块组合

将模块A与模块B进行LINK：
  → 静态检查：能力需求是否相互满足？
    否 → 组合失败
  → 静态检查：接口签名是否兼容？
    否 → 组合失败
  → 静态检查：不可变约束是否存在逻辑冲突？
    是 → 组合失败
  → 静态检查：REENTRANT_ALLOW声明是否一致？
    不一致 → 组合失败（机器世界没有"警告"）
  → 组合成功，生成新模块的静态接口

流程4：事务生命周期

BEGIN：
  → 记录当前全局版本号作为事务快照基准
  → 创建空的内存暂存写入集
  → 创建空的读取集
  → 创建空的副作用队列
  → 分配全局唯一事务ID和EFFECT序列号计数器
  → 进入事务上下文

执行中——读追踪：
  → REQUIRE中涉及的状态读取 → 自动记录StateId及版本号到读取集
  → HOLD_CHECK涉及的能力状态读取 → 同上
  → 对状态变量的直接取值 → 同上
  → 调用ENUM_SCOPE(scope_id) → 记录该Scope的结构版本号到读取集
  → 开发者无需手动声明READ(x)

执行中——修改与回滚：
  → 所有修改仅写入内存暂存写入集
  → 任何契约失败 → 自动ABORT
  → EFFECT暂存到副作用队列，不立即执行
  → SAVEPOINT创建命名回滚点
  → ROLLBACK_TO丢弃指定回滚点之后的修改、副作用和Scope结构变更

COMMIT：
  → 【进入全局提交临界区】：
      步骤1——冲突检测：
        基础检测：读取集中每个StateId的全局当前版本号 > 快照版本号？→ 冲突
        扩展检测：读取集中每个ScopeId的结构版本号 > 快照结构版本号？→ 幻读冲突
        任一冲突 → 退出临界区，ABORT
      步骤2——写入WAL：
        将写入集、Scope结构变更和副作用内容原子写入WAL并强制持久化
        WAL格式：COMMIT TX={id} VERSION={v} [WRITE...] [SCOPEBIND...] [SCOPEUNBIND...] [EFFECT...] END
      步骤3——状态固化：
        将写入集刷入全局状态空间
        Scope结构变更落地到ScopeRegistry
        每个被修改状态的版本号递增
        递增全局版本号
  → 【退出临界区】
  → 按顺序执行副作用队列中的EFFECT
  → 每条EFFECT执行后写EffectAck确认记录
  → 释放所有事务资源

ABORT：
  → 丢弃写入集和副作用队列
  → 释放所有事务资源
  → 按权限脱敏返回中止原因

流程5：并发冲突裁决

基础检测（读-写反依赖）：
  → 读取集中每个StateId的全局版本号 > 快照版本号？→ 冲突

扩展检测（幻读防御）：
  → 读取集中每个ScopeId的结构版本号 > 快照结构版本号？→ 幻读冲突

冲突裁决：
  → 任一冲突 → ABORT
  → 全部通过 → 允许提交

活锁防护：
  → 默认指数退避+随机抖动重试

流程6：崩溃自愈恢复

机器异常重启：
  → 扫描WAL
  → 重放所有COMMIT记录的修改（含state、scope变更）
  → 重建ScopeRegistry
  → 收集已提交但未确认EffectAck的副作用
  → 重试未确认副作用（携带原系统幂等键），重试后补写EffectAck
  → tx_id_counter从WAL中max_tx_id + 1续接
  → 机器进入就绪状态

流程7：错误信息脱敏

ABORT或拒绝调用时：
  → 调用方持有被访问状态的读取能力？→ 返回完整错误原因
  → 否则 → 统一返回"调用失败"

四、最小原语集

状态与事务类

原语 语义 参数
BEGIN 开始新事务，记录全局版本号快照，创建读取集/写入集/副作用队列 无
COMMIT 进入临界区：冲突检测→写WAL→状态固化→执行副作用 无
ABORT 丢弃写入集和副作用队列，释放上下文 中止原因（按权限脱敏）
SAVEPOINT 创建命名回滚点 回滚点名称
ROLLBACK_TO 回滚到指定SAVEPOINT（含Scope结构变更） 回滚点名称
CHECKPOINT 创建持久化状态检查点，截断WAL 无

契约类

原语 语义 检查时机
REQUIRE 声明前置条件；涉及的状态自动加入读取集 运行时，每次调用前
ENSURE 声明后置条件 运行时，执行后
INVARIANT 声明模块局部不变量 运行时，每次修改后
INVARIANT_SCOPE 声明跨状态不变量作用域，绑定动态集合 运行时；ENUM_SCOPE记录结构版本号；结构变更时递增结构版本号
ENUM_SCOPE 显式枚举动态集合；返回成员StateId列表，记录Scope结构版本号到读取集 运行时，显式调用
BIND_TO_SCOPE 将StateId绑定到指定Scope 运行时，变更集合结构时
CAP_REQUIRE 声明静态能力需求 组合期，LINK时
IMMUTABLE 声明不可变约束 组合期，LINK时
REENTRANT_ALLOW 声明允许同事务重入 组合期，LINK时（不一致直接拒绝）

能力类

原语 语义
GRANT 授予能力凭证；生成CapabilityId（确定性哈希）；在委托图中新增根节点
REVOKE 回收能力凭证；默认级联撤销；可声明CASCADE=FALSE
DELEGATE 委派能力给另一模块；可选CASCADE=FALSE；森林约束防环
HOLD_CHECK 检查调用方是否持有指定能力；涉及的能力状态自动加入读取集

副作用类

原语 语义
EFFECT 暂存副作用到事务队列；机器自动生成幂等键{事务ID}-{序列号}；COMMIT后执行；ABORT时清空

日志与恢复类

原语 语义
WAL_WRITE 在临界区内将最终修改原子写入WAL（机器内部自动调用）
EFFECT_ACK 副作用执行确认（机器内部自动调用）
RECOVER 从WAL恢复状态、能力图、Scope结构（机器启动时自动调用）

模块类

原语 语义
LOAD 加载模块，解析静态接口
LINK 组合两个模块，触发静态契约检查
UNLOAD 卸载模块，回收其能力和资源

五、完整示例

5.1 动态家庭共享额度（INVARIANT_SCOPE旗舰示例——幻读防御）

场景： 家庭账户组可动态增减成员，总额度不超过10000。关键设计：添加新成员不读取已有成员状态，新成员固定已用额度=0。提现操作通过ENUM_SCOPE显式枚举全体成员。并发时读写集无交集，只有SCOPE结构版本号能捕获冲突。

模块 动态家庭账户管理器：

  CAP_REQUIRE: 日志写入能力

  INVARIANT_SCOPE(family_group_scope, 集合[family_id])

  INVARIANT: sum(family_group_scope内所有账户.已用额度) <= 10000

  // 添加新成员：不读取任何已有成员状态，读取集为空
  操作 添加新成员(family_id, 新账户):
    BEGIN 事务:
      将新账户加入 family_id 集合
      BIND_TO_SCOPE(新账户.StateId, family_group_scope)
      新账户.已用额度 = 0  // 静态成立，无需校验全局sum
    COMMIT
    // 写入集：新账户创建 + Scope结构变更标记
    // 读取集：空
    // 此事务永远不会因读写冲突而ABORT
    // 但会导致family_group_scope的结构版本号递增

  // 提现：显式枚举动态集合
  操作 提现(family_id, 当前账户, 金额):
    BEGIN 事务:
      // 显式调用ENUM_SCOPE原语
      // 机器记录family_group_scope的结构版本号到读取集
      成员列表 = ENUM_SCOPE(family_group_scope)
      
      REQUIRE: sum(成员列表中各账户.已用额度) + 金额 <= 10000
      
      当前账户.已用额度 += 金额
      当前账户.余额 -= 金额

      EFFECT: 发送提现通知(当前账户, 金额)
    COMMIT
    // 若并发的ADD事务在此期间提交，SCOPE结构版本号已变
    // 扩展检测发现结构版本号不一致 → 幻读冲突 → ABORT
    // 重试后重新ENUM_SCOPE，新成员已纳入计算

魔鬼程序员测试：纯幻读场景

步骤 事务1：提现6000 事务2：添加新成员C 说明
初始 集合{A已用0, B已用0}，Scope结构版本=v1 同左 
BEGIN 快照：Scope结构版本=v1 快照：Scope结构版本=v1 
执行 ENUM_SCOPE→{A,B}，已用和=0 插入C，C已用=0 事务2不读取A、B任何状态
检查 0+6000≤10000 ✓ 无需校验 
写入 A已用=6000 C创建+Scope结构变更 事务1读取集含A已用=v1,B已用=v1；事务2未修改A、B→基础检测通过
COMMIT 先提交成功 后提交。Scope结构版本递增至v2 
若事务2先提交   
事务1提交 Scope结构版本v2>快照v1→幻读冲突→ABORT  基础检测通过，扩展检测捕获
重试 ENUM_SCOPE→{A,B,C}，已用和=6000，6000+6000=12000>10000→REQUIRE失败→ABORT  新成员被纳入，正确拒绝

为什么基础检测不够？ 事务2的写入集仅包含"创建C"和"Scope结构变更"，不包含对A、B的修改。事务1的读取集包含A.已用额度、B.已用额度——事务2从未修改这些。基础检测比对"我读过的状态是否被别人写过"——A和B的版本号都没变，通过。只有SCOPE的结构版本号能发现"我枚举时依赖的集合结构已经变了"。

为什么必须用ENUM_SCOPE显式原语？ 原则三：显式声明优于隐式推断。机器无法也不应猜测程序员的for循环意图。ENUM_SCOPE让程序员明确宣告"我要依赖这个动态集合的成员结构"，机器据此记录结构版本号。不调用ENUM_SCOPE就拿不到成员列表，从物理上杜绝绕过。

5.2 固定集合转账（基础检测已足够）

模块 账户管理器：

  INVARIANT: 所有账户.余额之和 == 总发行量

  操作 转账(从, 到, 金额):
    BEGIN 事务:
      REQUIRE: 从.余额 >= 金额
      HOLD_CHECK: 从.提取能力
      HOLD_CHECK: 到.存入能力

      SAVEPOINT(扣款):
        从.余额 -= 金额
      SAVEPOINT(入账):
        到.余额 += 金额

      EFFECT: 发送转账通知(从, 到, 金额)
    COMMIT
    // 读取集包含从.余额、到.余额
    // 若并发事务修改了同一账户，基础检测即可发现冲突

六、设计决策记录

6.1 为什么需要INVARIANT_SCOPE和ENUM_SCOPE？

基础检测进行读-写反依赖比对，对固定枚举的状态集合已足够。

INVARIANT_SCOPE的唯一不可替代价值是防御幻读式写偏斜：事务依赖的动态集合被并发事务静默变更成员结构，且该变更不读取已有成员状态，导致读写集无交集。

ENUM_SCOPE是触发此保护的显式原语。程序员必须显式调用它来枚举动态集合。机器不自动推断——这贯彻了原则三。

设计边界： INVARIANT_SCOPE仅保护动态集合的纯幻读场景。固定枚举集合用基础检测即可。

6.2 为什么能力纳入事务模型？

能力游离在事务外会导致：时序窗口攻击、崩溃后授权关系不一致、变更不可追溯。

纳入后能力和其他状态一样受快照隔离和WAL保护。

已知权衡： REVOKE仅对后续新事务生效，运行中事务不受影响。紧急撤销需操作系统级中断，不在抽象机器语义范围内。

6.3 为什么副作用暂存且携带系统幂等键？

事务内立即执行副作用，ABORT时无法撤回，原子性被打破。

EFFECT采用outbox模式，COMMIT后执行。幂等键由机器强制生成{事务ID}-{序列号}，程序员无法省略或篡改。崩溃恢复时根据EFFECT_ACK重试未确认副作用。

6.4 为什么重入默认禁止且不一致直接拒绝？

以太坊DAO事件的核心成因是重入绕过状态检查时序。默认禁止重入，显式声明REENTRANT_ALLOW才放行。

组合时双方声明不一致直接拒绝，不给警告。原则三：机器世界没有"警告"。

6.5 为什么采用全局提交临界区？

消除TOCTOU竞态：两个事务可能几乎同时通过冲突检测，然后都完成提交。临界区保证提交串行化。

6.6 模块为什么是无状态的？

模块是代码和契约的封装单元，不持有可变数据。所有状态属于机器的全局状态树。这消除了模块实例生命周期管理的复杂性，使LOAD/LINK/UNLOAD变成纯代码管理操作。

6.7 契约函数为什么必须是纯函数？

REQUIRE和ENSURE由宿主语言函数实现，但禁止副作用：不允许修改状态、不允许执行EFFECT、不允许访问外部IO。契约只在事务上下文中读取状态并返回布尔值。这保证契约检查本身不会成为副作用的漏洞。

6.8 CapabilityId为什么是确定性哈希而非随机生成？（V0.7新增）

Veritas 引擎的核心哲学是确定性可重放——WAL replay 两次必须产生完全一样的状态。随机生成的 CapabilityId 会导致两次 replay 产生不同 ID，与 State/Scope 的确定性设计原则直接冲突。

CapabilityId 沿用 StateId/ScopeId 的确定性哈希模式，输入为 Hash(grantor, grantee, resource, grant_sequence)。grant_sequence 是 Capability 子系统自己的单调计数器。

不可伪造性的保证：CapabilityId 的构造器不对宿主语言暴露，仅由 GRANT 原语生成。伪造的关键是拿不到构造权，不是猜不出数值。随机数在这里是抄了一个不适合本引擎设计哲学的教条。

6.9 能力委托图为什么是森林而非一般DAG？（V0.7新增）

约束：每个 (capability_id, holder) 组合只会被插入一次，且插入后的 HolderRecord 永不物理删除（revoke 只翻转 active 标志）。

推论：不可能成环——因为若 to 是 from 的祖先，to 必然已被插入过，插入时的 AlreadyInTree 检查会直接拒绝。无需额外环检测算法。

6.10 已知局限

1. 单机假设：分布式事务、网络分区、共识协议不在范围内。
2. EFFECT的"至少一次"语义：不保证恰好一次，依赖幂等键和重试。
3. 紧急撤销不可中断运行中事务：见6.2节。
4. 写偏斜保护的精确边界：见6.1节。
5. 原型阶段暂不支持动态LOAD/UNLOAD：模块系统启动时一次性加载。
6. StateId的稳定性：使用确定性哈希算法，详见运行时数据模型标准。
7. WAL采用文本格式而非二进制CRC32：原型阶段 cat wal.log 可读排障优先。CRC32留作P1.5。
